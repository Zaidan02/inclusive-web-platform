Les revues d'architecture

 Consistent à analyser la structuration des composants du
   logiciel de manière à détecter d'éventuels points
   d'inefficience pouvant être corrigés par refactoring.

 Doit rester relativement macroscopique, les revues de code
   traiteront les détails.

 Pour analyser cette structuration, il est nécessaire de se
   fonder sur la documentation, qui est souvent
   désynchronisée par rapport aux évolutions du logiciel.

     L'architecture d'un logiciel peut être représentée efficacement
      par les diagrammes UML, faciles à obtenir par reverse
      engineering. Ces diagrammes permettront d'identifier
      beaucoup d'inefficiences.
Les revues d'architecture

 La principale difficulté, est de détecter ces inefficiences, vu qu'elles
   dépendent du contexte du logiciel et du périmètre fonctionnel qu'il
   couvre.

     Des problèmes génériques ont néanmoins été formalisés et fournissent une
        bonne base pour analyser la qualité d'un logiciel.

 Pour le refactoring ce ne sont pas les qualités, mais les défauts que nous
   cherchons à identifier.

 Les anti-patterns, c.-à-d. les fausses solutions à de vrais problèmes (url du
   catalogue: http://c2.com/cgi/wiki?AntiPatternsCatalog) peuvent aider à
   identifier ces défauts et à les corriger par refactoring.

     Antipatterns = leçons par la négative pour la réussite de vos projets.

 Les problèmes détectés sont très difficiles à corriger, car ils touchent à la
   conception même du logiciel.

     Malheureusement, pour ce genre de problème, il faut effectuer une réécriture
        complète.

Le marteau en or

 Toute nouvelle technologie est attrayante:

     Elle se destine à régler beaucoup de problèmes
     Mais elle est mal maitrisée et souvent mal utilisée

         ◼ "C'est un peu comme quand on offre un marteau et qqes clous en plastique à
            un enfant. Apres les clous, tous les objets deviennent une cible potentielle"

 Dans le monde Java/J2EE, les EJB (Enterprise Java Beans) ont été comme
   un marteau en or:

     Destinés à être le Graal des composants d'entreprise, en dissociant les aspects
        techniques (sécurité, transaction, persistance, etc.) des aspects fonctionnels,
        réduits à leur plus simple expression, c.-à-d. presque programmables par des
        non-informaticiens.

     Mal maitrisés et mal conçus, ils ont malheureusement abouti à des résultats
        désastreux.

 Dans une revue d'architecture, il est utile d'identifier l'utilisation de
   marteaux en or, qui constituent des sources de complexité inutiles pour les
   besoins du logiciel,

     Il faut quand même reconnaitre que leur utilisation est souvent si
        profondément liée au code du logiciel, que leur éradication peut être longue
        et couteuse.

 La revue d'architecture doit être l'occasion de prendre du recul
   par rapport aux services que doit rendre le logiciel et
   d'identifier les machines de Rube Goldberg crées à cette fin.

 De telles "machines" peuvent apparaitre tardivement dans le

   de multiples évolutions non maitrisées (les fameuses

 Le cout d'éradication varie fortement d'une machine à une
   autre. Tout dépend de sa portée dans le logiciel. Une étude
   d'impact précise doit être menée pour bien estimer les
   conséquences d'un tel remplacement.
Réinventer la roue

 Réinventer la roue est extrêmement couteux pour les projets
   informatiques.

     Cela demande non seulement un investissement lors de la première
       version du logiciel mais des couts de maintenance dans les suivantes.

     C'est une occasion manquée pour la réutilisation.

 L'origine= méconnaissance de la part des développeurs des
   API à leur disposition (JEE ou autres)

     C'est une des problématiques adressées par les méthodes agiles que
       de favoriser la communication au sein des équipes afin de partager
       les connaissances.

 Lorsque la roue est complexe et mobilise inutilement vos
   ressources, la remplacer par un produit extérieur.

     Opération qui peut se révéler couteuse.
        ◼ Dans le cas des couches basses, les remplacer revient
          généralement à remplacer les fondements d'un bâtiment.

 Les dépendances cycliques rendent le code difficile à
   comprendre, et sa maintenance difficile.

     Modification d'une classe -> effet de bord sur les autres.

 Le plugin Eclipse Metrics (consacré à l'analyse quantitative)
   permet par exemple, de détecter graphiquement les

Les revues de code

 Nécessaires à tout projet de refactoring.
 Peuvent être automatisées en partie, mais

  nécessitent toujours le jugement humain pour
  déterminer si le code doit être refondu ou non.
 Les techniques précédentes sont macroscopiques et
  ne permettent pas de juger "sur pièces" de
  l'opportunité de procéder au refactoring.
Les revues de code automatisées

 Il existe plusieurs outils, commerciaux ou Open Source,
   capables d'analyser le code d'un logiciel pour identifier de
   mauvaises pratiques de programmation.

     Bien sûr, leur capacité est limitée
       ◼ Ne permettent de détecter que les problèmes simples, mais très
          fréquents.

     Leur fonctionnement est fondé sur un ensemble de règles
      auxquelles sont confrontés toutes les lignes de code source.
       ◼ Ces règles sont fournies en standard avec l'outil et dérivent de
          bonnes pratiques de développement définies par exemple par
          Sun, ou la communauté Java.

               ◼ Elles peuvent être paramétrées (définir la longueur max d'une ligne de
                  code) ou même être définies par l'utilisateur.
Les revues de code automatisées

 Parmi les problèmes typiquement détectés par ce type d'outils:
     Code mort: variables ou paramètres inutilisés, importations de package
       inutiles.
     Règles de nommage: respect des bonnes pratiques dans le nommage
       des différentes entités (classes, méthodes, packages, variables)
     Règles de formatage du code: lignes de code trop longues, etc…
     Règles sur la taille du code: classes ou méthodes trop longues, liste de
       paramètres excessives, etc.
     Règles sur la gestion des exceptions: clauses catch sans contenu,
       utilisation abusive de la classe Exception, etc.
     Règles sur la documentation javadoc: vérification de la présence de
       documentation, vérification de l'exhaustivité de la documentation, etc.
     Exemple de rapport avec PMD dans le slide suivant:

Les revues de code automatisées

 Les problèmes détectés avec ce type d'outils sont simples à corriger,
   peuvent même l'être de manière automatique (typiquement le
   formatage de code)

 Il est donc intéressant dans le cadre d'un projet de refactoring de
   prévoir la correction de tous ces problèmes.

 Important: Ce genre d'outils génèrent un nombre colossal d'erreurs, vu
   que certaines règles peu critiques peuvent générer beaucoup de
   bruit.
     Ceci peut être décourageant pour les programmeurs

 Il est donc essentiel pour réussir la mise en œuvre de ce genre d'outils
   de configurer intelligemment les règles de manière à adresser les
   problèmes critiques en premier.

 PMD offre un grand nombre de règles et permet de définir ses propres
   règles soit en java, soit avec XPath.

 Le détecteur de dupliquas fourni par PMD permet de détecter les
   duplications (copier-coller) de code.

L'analyse quantitative du logiciel

 La métrologie est un domaine en phase de maturation
 Elle fournit des indicateurs sur le logiciel qui pointent sur

  d'éventuelles inefficiences dans le logiciel, dont
  l'existence réelle doit être vérifiée en effectuant une
  revue de code (analyse qualitative).
 Les fondements de ces indicateurs sont souvent très
  empiriques.
    Ils sont donc parfois générateurs de fausses alarmes,

     tandis que des zones à refondre peuvent leur
     échapper.
Notion d'unité et de référence

 Au-delà de la notion d'unité, il est important d'avoir
  des références:

    Une mesure sans élément de comparaison est
     rarement utile pour juger des qualités de l'objet
     mesuré.

       ◼ Dans le cadre du logiciel, dire qu'un outil de conversion de
         monnaie contient mille lignes de code, ne donne pas
         beaucoup d'indication sur les qualités de ce logiciel.

       ◼ Il faut le comparer à un logiciel de même type pour
         pouvoir donner un sens à la mesure.
Le processus de mesurage

1. Définition des objectifs du mesurage

  1. Quoi (pas d’objectif trop large)

2. Définition de la méthode de mesurage

  1. Comment, outils. Etc…

3. Application de la méthode de mesurage

  1. Tenir compte du contexte, calibrage des outils

4. Analyse des résultats de mesurage

  1. Par comparaison
Le processus de mesurage

1. Définition des objectifs du mesurage

   a. Un objectif trop large (comme par exemple si le
       logiciel est de bonne qualité, ne saurait être couvert
       par une seule méthode de mesure)

2. Définition de la méthode de mesurage

   a. Bien connaître ce qui est mesuré

             Ex: si la propriété mesuré est "le nombre de lignes de code", alors
                  répondre aux questions suivantes: les lignes blanches, les lignes
                  de commentaires, les délimiteurs de blocs doivent-ils être
                  comptés?

   b. Et comment le mesurage est effectué: les moyens, les
       outils, etc…
Le processus de mesurage

3. Application de la méthode de mesurage: Il faut
     commencer par vérifier et calibrer les instruments de
     mesurage:

    a. Ex: un outil de mesure de performances Application Web, doit
         être testé sur une page Web vide, et dans l'environnement le
         plus stable (réseau, serveur, etc.…)

    b. Certains instruments de mesure peuvent avoir un effet sur la
         propriété observée (ex: les sondes qui permettent d'observer
         le taux d'utilisation du processeur, consomment elles-mêmes
         les ressources du processeur).
         La connaissance de ces effets permet de calibrer l'instrument
         de manière à produire les résultats les plus proches de la
         réalité.
Le processus de mesurage

4. Analyse des résultats de mesurage: En
    confrontant les mesures obtenues à des références
    afin de tirer l'information sur la propriété de
    l'objet observé.

   a. Les références peuvent avoir différentes origines:

       • Standards industriels, meilleures pratiques issues
           d'études empiriques, valeurs optimales issues d'études
           scientifiques, etc.
La métrologie logicielle

 La métrologie logicielle est à l'état embryonnaire.
     La notion d'unité est très peu formalisée (ex : lignes de code)
     Les références de comparaison empiriques
     Les évolutions technologiques ne facilitent pas la tache, pour chaque
       nouvelle technologie il faut de nouvelles références.

         ◼ Par exemple la notion de performance a été complètement bouleversée par
            l'augmentation de la puissance des microprocesseurs, et des architectures
            parallèles.

 En dépit, de leur faiblesse, les métriques sont utiles dans la mesure ou
   elles peuvent remonter des points d'attention, qu'il conviendra de
   vérifier par une revue de code.

 De plus elles ne permettent pas de détecter tous les problèmes.

Les mesures des dimensions du logiciel

 Mesures les plus simples à obtenir, mais comme bq de mesures
   logicielles varient d'une technologie à l'autre.

     Les dimensions d'un logiciel développé à l'aide d'un langage orienté
       objet, ne sont pas tout à fait les mêmes que celles d'un logiciel
       développé à l'aide d'un langage procédural (la notion d'objet faisant
       apparaitre de nouvelles dimensions).

     De surcroît, de plus en plus de logiciels reposent sur plusieurs
       technologies, ex: les technologies web avec JavaScript, XML, XSL, etc.
       qui apportent chacune leurs propres dimensions.

     Les unités utilisées pour ces différentes dimensions n'ont pas le même
       poids. Ex: une ligne de code source écrite dans un langage de 4eme
       génération a beaucoup plus de "puissance" qu'une ligne de source en
       assembleur.

 Il est donc primordial de savoir ce que l'on mesure et comment,
   pour pouvoir exploiter efficacement les résultats.
 Les dimensions globales

 Tel que le nombre de lignes de code source, le nombre de
   packages, le nombre de classes et d'interfaces

 Offrent une vision macroscopique
    Ne sont pas de très bons indicateurs pour détecter par
      exemple les zones du logiciel à inclure dans le refactoring, sauf
      quand elles prennent des valeurs extrêmes ou sans rapport
      avec la nature du logiciel.
    Cependant, en historisant les dimensions d'une version à l'autre
      du logiciel, et en les comparant avec les évolutions
      correspondantes, il est possible de détecter certains
      phénomènes macroscopiques dénotant une érosion de
      l'architecture du logiciel.

        ◼ Ex: le cas de la croissance inexplicable du nombre de lignes de code du
          logiciel, à la suite d'une évolution mineure.
Le nombre de lignes de code source

 La plus simple à mesurer , mais pose un certain nombre de problèmes.

     Qu'est-ce qu'une ligne de code source
     Quelle est la puissance d'une ligne de code source
     Comment compter les lignes dans un logiciel intégrant différentes technologies?

 Malheureusement: Pas de réponse unique!!
 Au niveau de l'ensemble du logiciel, c'est une métrique non utilisable

   pour détecter les cibles de refactoring, par contre au niveau d'une
   certaine partie du logiciel, telle que par exemple une classe Java, ca
   permet de détecter certains problèmes, à condition d'avoir des références.

     Par exemple, dans le cadre de l'implémentation d'un algorithme de tri, il est
        possible de détecter si le nombre de lignes de code est cohérent avec la
        complexité de l'algorithme.

 Les mesures historiées couplées aux évolutions du logiciel constituent aussi
   de bonnes références pour l'interprétation de cette métrique:

     Par exemple une classe Java ayant fortement augmenté en nombre de lignes de
        code sans corrélation évidente avec l'évolution du logiciel, peut être devenue
        une classe "poubelle" et nécessiter une refonte.
Le nombre de packages

 C'est un indicateur de regroupement des composants du
   logiciel en des entités organisationnelles.

 Les packages ayant une sémantique importante et non
   quantifiable, cet indicateur n'est pas d'une grande aide
   pour savoir si le regroupement est pertinent ou non.

 Cette métrique est utilisée pour détecter des valeurs
   extrêmes (petites ou grandes) injustifiables du point de
   vue de la nature du logiciel:

     Ex: un seul package pour un logiciel de traitement de texte.
Nombre de classes et d'interfaces

 Comme le nombre de packages, cet indicateur ne permet
   pas de juger réellement de la pertinence des classes et
   interfaces comptées.

 Mais en comptant ce nombre pour un domaine
   fonctionnel particulier, il est possible d'estimer s'il est
   cohérent par rapport à la richesse du domaine.

 On peut aussi comparer la différence entre les classes du
   logiciel, et celles ayant été modélisées lors des phases de
   conception successives.

     Une forte déviation peut indiquer:
       ◼ soit une mauvaise synchronisation entre la conception et la
          réalisation,
       ◼ soit l'existence de classes développées de manière opportuniste
          et non optimale.

interface

 Utilisées comme base pour les mesures de risques
  abordées plus loin dans ce chapitre.

 Comme les valeurs précédentes, elles ne sont
  pertinentes que dans la recherche des valeurs
  extrêmes ou incohérentes par rapport à la
  complexité fonctionnelle correspondante.

 4 dimensions:

        ◼ Nombre de méthodes
        ◼ Nombre de méthodes redéfinies
        ◼ Nombre d'attributs
        ◼ Nombre de descendants directs/indirects

interface

 Du point de vue de la conception orienté objet
  il faut regarder:

    Si le nombre de méthodes redéfinies est
     important:

      ◼ Peut indiquer une mauvaise utilisation de l'héritage

    Et un nombre de descendants important:

      ◼ Fait de la classe ancêtre un point sensible du logiciel, et
         une modification de cet ancêtre peut avoir des effets de
         bord très important sur les descendants.

   Métrique 2: profondeur de l'arbre

   d'héritage (DIT)

42

       La métrique DIT, (depth of Inheritance Tree) correspond simplement à la
         distance maximale entre un nœud et la racine de l'arbre d'héritage de la
         classe concernée.

       L'héritage est susceptible d'augmenter la complexité d'un logiciel.

       Cette métrique importante est calculée pour chaque classe, elle sert de
         déterminer pour chaque classe le poids de son héritage.

       C&K ont suggéré les conséquences suivantes d'une DIT 

             Des arbres profonds implique un design plus complexe, puisqu'il y a plus de
                méthodes et de classes qui rentrent en jeu-> conception moins claire ->
                maintenance plus difficile.

             Plus une classe est profonde dans l'hiérarchie d'héritage, plus elle hérite d'un
                grand nombre de méthodes, rendant plus complexe la prédiction de son
                comportement -> phénomène de dégénérescence (plus aucun rapport avec les
                ancêtres)

             Plus une classe est profonde dans l'hiérarchie d'héritage, le potentiel de
                réutilisation des méthodes héritées devient plus grand.

La complexité cyclomatique

 Mesure très répandue (introduite par Thomas McCabe en 1976).
 Elle fournit un nombre unique représentant le nombre de chemins

   linéairement indépendants dans un programme.
     Cela donne une idée de l'effort à fournir pour tester le programme.
 Conçue de manière à être le plus indépendante des langages
   auxquels elle est appliquée.
     Car la mesure repose sur une représentation du programme à mesurer

       sous forme de graphe.
 Plusieurs études ont montré une corrélation entre la complexité

   cyclomatique d'un programme et la fréquence des erreurs au niveau
   de ce programme.
     Une complexité cyclomatique basse semble contribuer à la création

       de programmes de meilleure qualité.
La complexité cyclomatique

 Le SEI (Software Engeneering Institute) de l'université Carnegie Mellon
   propose une table pour estimer le risque associé à un programme à
   partir de sa complexité cyclomatique.

  Complexité cyclomatique Niveau de risque

1-10   Programme simple, sans veritable risque
11-20  Programme modérément complexe, et risqué
21-50  Programme complexe, et hautement risqué
>50    Programme non testable, et extrêmement risqué

 La dépendance vis-à vis d'entités extérieures est source
   d'instabilité du fait des effets de bord potentiels issus de la
   modification de ces dernières.

 La métrique d'instabilité d'un package est calculée en
   divisant le nombre de classes du package observé
   dépendant des classes extérieures (couplage efférent) par
   la somme de ce nombre et du nombre des classes extérieurs
   dépendant des classes du package (couplage afférent)

 Un indice d'instabilité fort indique une fragilité par
   rapport à son environnement extérieur.

     Cependant une valeur forte peut être rencontrée sur la couche
      haute (proche de l'IHM) vis-à-vis des couches basses sans que
      cela soit anormal.
