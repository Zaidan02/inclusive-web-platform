       droits d ’accès différents. 200 personnes ont quotidiennement accès au

       une porte d ’accès munie d’un lecteur de badge spécifique.

Gestion de configuration et Intégration

  ❑ Gestion de Configuration:

       ◼ permettre la gestion des composants du logiciel, d'en maîtriser l'évolution
            et les mises à jour tout au long du processus de développement
            (documentation homogène)

       ◼ Les IDE permettent de gérer de façon plus cohérente les documents
            relatifs à un logiciel.

  ❑ Intégration:

       ◼ assembler tout ou partie des composants logiciels pour obtenir un
            système exécutable

       ◼ existe souvent plusieurs choix possibles pour certains composants ->
            variantes du logiciel (ex: pour des systèmes d'exploitation différents)

       ◼ utilise la gestion de configuration pour :
            ❑ assembler des versions cohérentes de composants
            ❑ gérer des variantes du logiciel

◼ Consider a microservice architecture. Each service in a microservice
    architecture uses configuration metadata to register itself and initialize.
    Some examples of software configuration metadata are:

     ❑ Specifications of computational hardware resource allocations for CPU, RAM,
         etc.

     ❑ Endpoints that specify external connections to other services, databases, or
         domains

     ❑ Secrets like passwords and encryption keys

◼ Configuration values will often be added, removed, or modified. Without
    version control this can cause problems.

◼ Version control and configuration management solve this problem by adding
    visibility to configuration modifications.

     ❑ When a change is made to configuration data, the version control system tracks
         it, which allows team members to review an audit trail of modifications.

How configuration management fits

with DevOps, CI/CD and agile

◼ Configuration data has historically been hard to manage.

    ❑ It's not really code so it’s not immediately put in version control and it’s
        not first-class data so It isn’t stored in a primary database.

    ❑ Traditional and small scale system administration is usually done with a
        collection of scripts and ad-hoc processes.

    ❑ Configuration data can be overlooked at times, but it is critical to system
        operation.

◼ The rise of cloud infrastructures has led to the development
   and adoption of new patterns of infrastructure management.

    ❑ These new cloud platforms allow teams to specify the hardware
        resources and network connections they need provisioned through
        human and machine readable data files like YAML.

    ❑ The data files are then read and the infrastructure is provisioned in the
        cloud. This pattern is called infrastructure as code (IaC).

How configuration management fits
with DevOps, CI/CD and agile

◼ Configuration management is a key part of a DevOps lifecycle.
   DevOps configuration brings automation to infrastructure
   management and deployment.

◼ CI/CD configuration management utilizes pull request-based

   changes to a live software system.

◼ This same flow can be applied to configuration changes.
◼ CI/CD can be set up so that approved configuration change

   requests can immediately be deployed to a running system.

◼ le développement est-il correct par rapport à la

Modèle en cascade (waterfall model)

◼ Historiquement, la première tentative pour mettre de la rigueur
   dans le ‘développement sauvage’ (coder et corriger ou ‘code
   and fix’) a consisté à distinguer une phase d’analyse avant la
   phase d’implantation (séparation des questions).

◼ Très vite, pendant les années 70, on s’est aperçu qu’un plus
   grand nombre d’étapes étaient nécessaires pour organiser le
   développement des applications complexes.

◼ Le modèle en cascade décrit cette succession d’étapes

 Modèle en Cascade

 ◼ Cycle de vie linéaire sans aucune évaluation
    entre le début du projet et la validation

 ◼ une étape doit se terminer à une certaine date,
    par la production de certains documents ou
    logiciels.

 ◼ les résultats de l'étape sont soumis à une revue
    approfondie, et on ne passe à l'étape suivante
    que quand ils sont jugés satisfaisants.

In 1985, the United States Department of Defense captured this approach in DOD-STD-
2167A, their standards for working with software development contractors, which stated that
"the contractor shall implement a software development cycle that includes the following six
phases: Software Requirement Analysis, Preliminary Design, Detailed Design, Coding and
Unit Testing, Integration, and Testing".[7]

     ❑ Il n'y a pas de grand pilier directionnel, aucune façon de faire ou standard

◼ Team Dynamics:

   ❑ Success or failure often due to non-technical issues.

◼ Team Structure:

   ❑ Five defined roles: Team Leader, Development Manager,

   ❑ Ineffective leadership, lack of cooperation, procrastination, poor

       quality, and ensures that projects are completed on time and
       within budget.

PSP (Personal Software Process)

◼ Logic of Time Management:

     ❑ Track and compare time spent to improve planning.
     ❑ Categorize activities and record time spent.
     ❑ Use an engineering notebook for time tracking.

◼ Managing Variable Time:

     ❑ Prioritize tasks and set deadlines.
     ❑ Identify activities to do when time permits.

◼ Managing Commitments:

     ❑ Analyze and plan before committing.
     ❑ Document agreements and notify if unable to meet commitments.

◼ Handling Missed Commitments:

     ❑ Seek alternative strategies and add resources if needed.
     ❑ Avoid last-minute problem recognition.

◼ Why PSP?:

     ❑ Quality of software is determined by the developer's knowledge, discipline, and
         commitment.

     ❑ Measure, track, and analyze performance to improve practices.

Capacity vs Velocity

◼ Capacity is specific to an individual sprint and guides
   sprint planning.

◼ Velocity is a historical metric based on past sprints
   and is used for longer-term planning (i.e release
   planning) and predicting the team's overall capability.

◼ Capacity Adjustment: While velocity is a valuable
   guideline, the team may need to consider any
   changes in their capacity or special circumstances for
   the upcoming sprint. If there are team members on
   vacation or other events affecting availability, they
   may need to adjust their commitment accordingly.

 SaFe (1/2)

◼ Scaled Agile Framework (SAFe): A set of procedures
   and practices designed to help large organizations with
   multiple teams to be more agile.

◼ Agile Release Train (ART): A team that is made up of
   Agile teams.

   ❑ A cross-functional group of 50 to 125 people who work on the
       same project.

   ❑ The members of the ART are aligned to a shared business and
       technological mission.

   ❑ This team plans and commits to the work that will be completed
       in the PI (Program Increment)

                                                                                                                                                                    269
SaFe(2/2)

◼ Program Increment (PI): A time-managed period (usually eight
   to 12 weeks long) in a SAFe environment. A PI consists of a
   series of iterations within a fixed schedule that defines the work
   that will be done by multiple Agile teams during each
   iteration.

    ❑ PI is similar to a sprint (scrum) but scaled for large corporations with
        multiple Agile teams across an organization all working toward the same
        goal.

◼ PI planning: An activity with the intent of ensuring that the ART
   is on the same track moving in the same direction. PI planning
   events are face-to-face meetings held every eight to 12 weeks
   after the previous PI.

    ❑ Multiple teams come together to plan and define the work that needs to
        be done, review backlogs, discuss which features will add value, create
        or update the product roadmap, and identify risks and dependencies.
