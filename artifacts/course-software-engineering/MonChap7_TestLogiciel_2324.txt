     différences entre les résultats attendus et les résultats obtenus. »

          Définition du test

• Est-ce que le logiciel fonctionne comme prévu ?
• Le test est souvent associé avec les termes vérification et validation.

• La validation est le moyen de confirmer le respect d’exigences
    déterminées pour une utilisation spécifique prévue.

      – Validation : Faisons-nous le travail attendu ?

• La Vérification est l’action de confirmer la satisfaction des exigences
    spécifiques via l’étude et la mise à disposition de preuves objectives.

      – Vérification : Faisons-nous le travail correctement ?

             La v&v est une part cruciale du développement, (40% du
             budget global): Le test est de loin la méthode la plus
             utilisée.
     Deux perspectives du test

• Tests par l’affirmation (positive testing, validation testing): Pour démontrer la
    qualité à postériori
      – « Le test est une activité destinée à déterminer si l’évaluation d’une
         caractéristique ou d’une aptitude d’un programme ou d’un système donne les
         résultats requis. » -> test-to-pass
      – Montrer que le système agit comme il est censé le faire, c'est l'analyse de la
         spécification des exigences qui permet de concevoir les jeux d'essai.
      – Implique des acteurs externes à l’entreprise

• Tests par la négation (negative testing, defect testing): Pour améliorer la qualité
      – « Tester c’est exécuter le programme dans l’intention d’y trouver des
         anomalies ou des défauts » -> test-to-fail
      – Sert fréquemment à examiner les aspects non décrits, mal formulés, ou
         incomplètement définis dans les documents de spécification.
      – Interne à l’entreprise
Les classes de défaut
Les erreurs peuvent être de divers ordres.

Il peut s'agir d'erreurs :

      - de calcul: x=x+2 au lieu de x=x-2
      - de logique: if a > b au lieu de if a < b
      - d'entrée / sortie: mauvaise description, conversion, formatage, des
      entrées/sorties
      - de traitement des données: dépassement de tableau, variable non définie,
      - d'interface (communication entre les programmes): on appelle p1 au lieu de
      p2, mauvais passage de paramètre
      -de définition des données: int au lieu de long, etc…
      -…

          Ces erreurs représentent 90% des cas décelés.

Le test Manuel :

Les tests sont exécutés par le testeur qui vérifie les traitements… et compare les
résultats obtenus avec ceux attendus.

Ces tests sont fastidieux et offrent une plus grande possibilité d’erreurs humaines.
Ces tests sont très vite ingérables dans le cas d’applications de grandes tailles.

Le test Automatique :

Le testeur est en partie déchargé des tests dans la mesure où les tests sont
réalisés par des outils (JUnit par exemple dans le monde Java).
                        Selon les modalités du test

Statiques :

Les tests sont réalisés «par l'humain» (testeur), sans machine, par lecture du code dans le
but de trouver des erreurs (revue de code, estimation de la complexité, détection d’erreurs
indépendantes de l’application, vue globale algorithmique, etc. )
•Limites tests statiques: être dissociés de l’exécution réelle du programme

Dynamiques :

On exécute le système de manière à tester l’ensemble des caractéristiques. Produire des DT,
à partir du code source et spécification, qui exécuteront un ensemble de comportements,
comparer les résultats avec ceux attendus…

                                         Selon les niveaux de tests

Il s’agit de tests réalisés tout au long de la vie du logiciel (cycle de vie).

Unitaires : s'assurer que les composants logiciels pris individuellement sont

conformes à leurs spécifications et prêts à être regroupés.

D’intégration : s'assurer que les interfaces des composants sont cohérentes

entre elles et que le résultat de leur intégration permet de réaliser les
fonctionnalités prévues.

Système : s'assurer que le système complet, matériel et logiciel, correspond bien

à la définition des besoins tels qu'ils avaient été exprimés. On parle de validation
ou de recette.

De non régression : vérifier que la correction des erreurs n'a pas affecté les

parties déjà développées et testées. Cela consiste à systématiquement rejouer les
tests déjà exécutés.

• Pour mener une inspection, il faut:

    – Disposer d'une spécification précise du code
    – Disposer d'un membre de l'équipe familiarisé avec les

       standards adoptés
    – Disposer d'une version de code dépourvue de toute

       erreur de syntaxe
    – Que la direction soit prête à accepter le cout de la

       vérification statique
    – Que l'inspection soit acceptée par le chef du projet
    – Suite à une inspection, le programmeur doit corriger son

       programme avant de procéder à une réinspection
              Code review

• On étudie le code du programme et on détecte les fautes
   avant l'exécution, en s'aidant souvent d'une check-list des
   défauts les plus courants:

     – L'utilisation de variables non initialisées
     – Les sauts dans les boucles
     – Les affectations incompatibles
     – Les boucles infinies
     – Les débordements de tableaux
     – Les allocations et libérations impropres de zones mémoire.
     – Les mauvaises correspondances entre paramètres formels et effectifs,
     – Les tests d'égalité entre valeurs flottantes, etc…
Java Inspection Check List (Document complet
                    sur moodle)

  • Variable and Constant Declaration Defects (VC)

         – Are descriptive variable and constant names used in accord with naming conventions?
         – Are there variables with confusingly similar names?
         – Is every variable properly initialized?
         – Could any non-local variables be made local?
         – Are there variables that should be constants?

  • Function Definition Defects (FD)

         – Are descriptive function names used in accord with naming conventions?
         – Is every function parameter value checked before being used?

  • Class Definition Defects (CD)

         – Does each class have an appropriate constructor ?
         – For each member of every class: Could access to the member be further restricted?
         – Do any derived classes have common members that should be in the base class?
         – Can the class inheritance hierarchy be simplified?
Java Inspection Check List: Exemple

• Packaging Defects (LP)

      – For each file: Does it contain only one class?
      – For each function: Is it no more than about 60 lines long?
      – For each class: Is no more than 2000 lines long (Sun Coding Standard) ?

• Performance Defects (PE)

      – Can better data structures or more efficient algorithms be used?
      – Are logical tests arranged such that the often successful and inexpensive tests

         precede the more expensive and less frequently successful tests?
      – Can the cost of recomputing a value be reduced by computing it once and

         storing the results?
      – Can a computation be moved outside a loop?
      – Are there tests within a loop that do not need to be done?
      – Are there two loops operating on the same data that can be combined into

         one?
   Graphe de contrôle: Définition

• Un graphe de contrôle présente la structure de contrôle du code.
• Chaque nœud (représenté par un cercle) correspond à un bloc de code qui

    ne contient qu'un seul trajet possible.
• Cela veut dire qu'il n'y a qu'une entrée et qu'une seule sortie à ce bloc.

      – Si une instruction du bloc est exécutée, alors toutes les autres le sont
         également.

• Les flèches entre les nœuds représentent les transferts de contrôle
    possibles: si le bloc B peut être exécuté juste après que le bloc A l'a été, il
    doit y avoir une flèche de A vers B.

• Pour obtenir des diagrammes de contrôle corrects:

      – il doit y avoir un nœud de départ
      – Pour chaque nœud, il doit exister un chemin permettant de l'atteindre en

         partant du nœud de départ.
      – Pour chaque nœud, il doit exister un chemin permettant d'atteindre un nœud

         de fin.

  Méthodes de tests dynamiques:
           Processus du test

1. Choisir un cas de tests (CT) = scénario à exécuter
2. Estimer le résultat attendu (Oracle)
3. Déterminer une donnée de test (DT) déclenchant CT

     (concrétisation)
4. Exécuter le programme sur la DT (script de test)
5. Comparer le résultat obtenu au résultat attendu (verdict)

    – Une différence entre les résultats obtenus et ceux attendus pour les
          entrées sélectionnées révèle une défaillance

6. rapport de test (pass/fail)

          Pour déterminer qu'il y a différence, il faut avoir au préalable
          déterminé un oracle, c'est à dire un prédicat spécifiant le
          domaine des valeurs attendues comme correctes à l'exécution
          du jeu d'essai.

 Comment choisir le jeu de tests?
         Méthodes aléatoires

• Le jeu de tests est sélectionné au hasard sur le domaine des entrées du
    programme.

• Le domaine des entrées du programme est déterminé à l’aide de
    l’interface de la spécification ou de l’interface du programme.

• Avantages:

      – Ces méthodes ont le double avantage de la rapidité et de l'objectivité.
      – Il est également plus facile d'appliquer des considérations statistiques dans ce

         cas.

       Couverture des instructions

• Objectifs

      – Exécuter au moins une fois toute instruction du programme
      – Détecter des instructions fautives

• Justification – hypothèses

      – Une seule exécution d’une instruction fautive causera une défaillance

• Limites

      – S1;
      – if C then S2;
      – S3;

• C = vrai satisfait le critère (S1, S2 et S3 exécutés).
• C = faux potentiellement jamais testé.
• C'est le test structurel le plus simple, souvent appelé C0

• Appliquer ce critère consiste à sélectionner des données de test jusqu'à ce
    qu'un outil de couverture indique que toutes les instructions de code ont
    été exécutées.

• Objectifs

      – Exécuter au moins une fois chaque branche

             • Emprunter les deux directions possibles au niveau de chaque décision

      – Mettre en évidence des défauts dans les instructions conditionnelles ou
         itératives

• Justification – hypothèses

      – Deux passages par la condition (vrai-faux) suffisent pour mettre en évidence
         un défaut

• Limites

      – if C1 then S1 else S2;
      – if C2 then S3 else S4;
      – (C1, C2) = (F, F) et (V, V) satisfont le critère.
      – (F, V) et (V, F) jamais testés.

• Le test de toutes les branches est un critère plus complet, souvent appelé,

    du jeu est négatif.

Quand estime-t-on que le programme n’a plus besoin d’être testé?

           Un programme n’a plus besoin d’être testé, lorsque
           l’efficacité du jeu de tests sélectionné est conforme à
           certains critères de qualité, et lorsque ce jeu de tests

           correcte du code (ex: transformation des signes - en

           avec le nombre de mutants sur lesquels le test détecte
           une anomalie.

 Calcul direct du nombre de Mc Cabe

• Produire un graphe de contrôle et l'analyser peut s'avérer
   long dans le cas de programmes complexes

• Mc Cabe a introduit une nouvelle manière de calculer la
   complexité structurelle

• C=∏+1
• avec ∏ le nombre de décisions du code

     – Une instruction IF compte pour 1 décision
     – Une boucle FOR ou WHILE compte pour 1 décision
     – Une instruction CASE ou tout autre embranchement multiple compte

       pour une décision de moins que le nombre d'alternatives
    Métriques de Mac Cabe: Remarques

1. les analyseurs statiques du marché, peuvent déclarer calculer la même
     métrique et pourtant produire des réponses différentes pour le même
     morceau de code.

      – Selon que l’on décompose une condition composée ou non, par exemple : IF
         A=B AND C=D THEN…

               • Nbre de decision =1 si un predicat -> C=2
               • Nbre de decision =2 si on decompose -> C=3

2. Valeur de seuil:

     – Il est bon d’avoir une idée des valeurs qui sont raisonnables ou qui ne le sont
           pas.

     – Après avoir analysé un projet de grande envergure, Mc Cabe a constaté que
           les modules dont le nombre cyclomatique dépassait 10 avaient connu bien
           plus de problèmes et posaient bien plus de difficultés de maintenance que
           ceux dont le nombre cyclomatique étaient inférieur à cette valeur -> Donc 10
           est considérée comme la valeur seuil.

     – Dans ce cas, il est souhaitable d’essayer de décomposer le module pour
           réduire cette valeur.
       Métriques de Halstead

• Métriques pour la complexité d'un programme

      – Fondées empiriquement

• Toujours considérées comme valides
• Entités de base

      – Opérandes : jetons qui contiennent une valeur
      – Operateurs : tout le reste (virgules, parenthèses, operateurs arithmétiques...)

• Mesures de base de la taille d'un programme ayant:

      – η1 (êta) : nombre d'operateurs distincts
      – η2 : nombre d' opérandes distincts

    η = η 1 + η 2 : nombre total de jetons distincts
                    Métriques de Halstead

• Exemple
• z = 0;
• while x > 0

      – z = z + y;
      – x = x - 1;

• end-while
• print (z);

• Operateurs :      = ; while-end-while > + - print ()

• Operandes :       z 0 x y 1

• On a donc : η1 = 8 et η2=5
       Métriques de Halstead

• Longueur d'un programme

      – N1 : Nombre total d' operateurs
      – N2 : Nombre total d'opérandes

• N = N1 + N2 : Nombre total de jetons
• Dans notre exemple:

      – N1=14 et N2=12, ce qui donne N=26

• Estimation de la longueur:

      – C'est la plus simple des formules de prédiction de Halstead.
           Elle permet d'obtenir une estimation de la longueur totale du programme en nombre de
           jetons à partir du nombre d'opérateurs et d'opérandes distincts utilisés:

      – Dans notre exemple : Nest = 8 *log2(8) + 5 * log2(5) = 8 * 3 + 5 * 2.32 = 35.6
      – Ici, Nest >> N
      – En pratique, Si la différence entre N et Nest est supérieure à 30%, il vaut mieux renoncer

           à utiliser les autres mesures de Halstead, telles que:
             • Le nombre de bugs dans un programme
             • Testing Time

• Objectif des tests d’intégration

     – Validation des interfaces des composants
     – Validation de l’interaction matérielle

• Objectif des tests métiers

     – Vérifier la bonne mise en œuvre des besoins utilisateurs.
     – Tests fonctionnels visant à contrôler la réponse de l’application aux

        différents évènements du métier.

• Conclusion : les tests d’intégration représentent la partie
   “technique” des tests métier. Ainsi, les tests d’intégration se
   focaliseront sur le fonctionnement et les aspects techniques
   de l’assemblage des différents composants ; ils n’entreront
   pas dans le détail du fonctionnel
           Objectifs des tests d’intégration par
              rapport aux tests métiers

• Périmètre couvert

     – le bon dialogue entre les modules,

             • Appel, transmission de données, compatibilité

     – le fonctionnement des menus de module métier,
     – le fonctionnement des types d’habilitation et types de profils

        utilisateurs : les droits d’accès, le droit d’utiliser les différents modes
        pour chaque dialogue technique, etc.
     – Synchronisations, points de reprises

• Périmètre exclus

     – les vérifications liées à une action fonctionnelle (à un « business event »),
     – la création des différentes entités fonctionnelles (par exemple, la

        création d’un fournisseur dans une application commerciale).

                  if (p!=null){

                                    Account a = new Account(p, amount, overdraft, accountNumbers);
                                    p.addAccounts(a);
                                    this.addAccounts(a);
                  }
                  //if the client does not exist, add it to the bank's list of clients and create account
                  else{
                                    Person client = new Person(name);
                                    this.addClients(client);
                                    Account a = new Account(client, amount, overdraft, accountNumbers);
                                    client.addAccounts(a);
                                    this.addAccounts(a);
                  }
                  return accountNumbers;
}
